## 1. Nonnegotiable scope

- Fix C implements a **restricted Python Worker** and an **instance-local observer**, not a second trainer. The only training call is inherited `Sd3NetworkTrainer.train(args)`; no extra forward, backward, optimizer/scheduler step, save, or load is permitted.
- Only candidate case IDs `r1-adamw-accum1` and `r2-muon-adamw-fallback-accum2`, single-process CUDA BF16, fixed 512×512 DreamBooth references, and production `networks.lora_sd3` may run. R1 has one physical AdamW child and one prepared batch/epoch; R2 has disjoint physical Muon and AdamW-fallback children and two prepared batches/epoch.
- **Do not change** `scripts/dev/train_network.py`, `scripts/dev/sd3_train_network.py`, `mikazuki/parameter_policy_torch.py`, any production Full-BF16 qualification record, R0 evidence or WebUI. `sd3-lora` remains persistently `pending`; local Worker evidence is not production qualification.
- A Worker may publish only `incomplete`, `fail`, or `worker_complete` (the existing Fix B publisher forbids `pass`). Fix D alone authenticates subprocess identity, accepted Fresh ancestry and the final aggregate outcome. No real GPU run in C0/C1.
- Fix B `support` remains importable without Torch. The Worker top-level import and its CLI parsing/preflight must also remain Torch-free; runtime/Observer imports happen only after strict no-Torch preflight and Ticket claim.

## 6. Phase geometry, events and evidence authority

- Fixed **total** `max_train_steps=2` for Fresh and Resume (Scheduler Identity). The real **Fresh** trainer executes Steps 1 and 2 and writes both, but the **authoritative Fresh handoff** is saved Step-1. The independent **Resume** trainer begins from Fresh Step-1 and executes Step-2. For R1 there is 1 actual batch/backward per logical step; for R2 there are 2. The event verifier must not reject the legitimate extra Fresh Step-2 or train-end save, nor falsely bind them to the Step-1 handoff.
- Each event must contain `run_id, phase_id, case_id, source_commit, event_seq, event_type, logical_step`, and a documented event-specific shape (microbatch index, sample identity, sync flag, Profile, before/after fingerprints, checkpoint ID). Sequence starts at 1 and is strictly increasing, with no duplicate or unknown event type.
- Event types (v1): `batch_started`, `backward_completed`, `physical_child_stepped`, `physical_scheduler_stepped`, `checkpoint_saved`, `checkpoint_loaded`, `train_completed`. A physical event requires the actual wrapped underlying method to have returned successfully; **no** fabricated `child_step` on a non-sync microbatch.
- Per effective step require ordered Batch→Backward pairs, correct sample uniqueness, exactly one physical Step per required child and Scheduler, actual change where required and post-save binding. R2 no-sync state is verified by **next** Batch-start fingerprints. Resume requires `checkpoint_loaded` before any training Batch. Expected target save steps: Fresh=1, Resume=2; Fresh Step-2 may appear as an additional non-handoff event.
- Pure Host `validate_worker_event_stream` verifies schema/order/count/coherence on **fixture or Worker-supplied metadata only** and must return `status='timeline_metadata_valid'`, never CUDA PASS. Fix D separately correlates immutable tickets, subprocess exit status, physical evidence snapshots, source/submodule/environment identities and completed checkpoint files.
- `publish_phase_result` remains no-overwrite and status limited to `incomplete|fail|worker_complete`; after the entire lease exits, the Worker may publish `worker_complete` with its evidence digest only. Neither C0 nor C1 changes a production qualification row.
